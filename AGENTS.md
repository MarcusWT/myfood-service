# AGENTS.md

## Commands
- `npm run dev` — tsx watch server (entrypoint `src/index.ts`)
- `npm run build` — `tsc` to `dist/`
- `npm start` — runs the compiled server (`node dist/index.js`); requires `npm run build` first
- `npm test` — `vitest run` (all tests, runs under `NODE_ENV=test` automatically); `npm run test:watch` for watch mode; `npm run test:coverage` for coverage
- Single test file: `npx vitest run path/to/file.test.ts`
- `npm run typecheck` — `tsc --noEmit`
- `npm run lint` — runs `eslint src` using `eslint.config.js` (flat config, `typescript-eslint`); passes clean as of this writing.
- CI (`.github/workflows/ci.yml`) runs lint, typecheck, and test on every push/PR via GitHub Actions, Node version pinned via `.nvmrc`. No secrets are required — see Environment/config below.

## Environment / config
- `.env` is auto-loaded via `dotenv/config` imported at the top of `src/config.ts` (`dotenv` is a real dependency). `cp .env.example .env` is sufficient for `npm run dev`/`npm start`.
- **`JWT_SECRET` is required outside `test` env — the app throws at startup if it is unset, empty, or left as the literal `.env.example` placeholder value.** Under `NODE_ENV=test` (which `vitest` sets automatically), `config.ts` falls back to a fixed test secret, so `npm test` and CI need no secrets configured at all.
- `SPOONACULAR_API_KEY` missing only logs a warning at startup (`src/config.ts`); it does not throw. Recipe endpoints will fail at request time instead.
- `DB_PATH` defaults to `./data/myfood.db`; `src/index.ts` creates the parent dir via `fs.mkdirSync` on startup. Set `DB_PATH=:memory:` to use `InMemoryFoodItemRepository`/`InMemoryUserRepository` instead of SQLite (see Architecture below).
- Other configurable env vars (all read in `src/config.ts`, all have sensible defaults, none required): `PORT`, `LOG_LEVEL`, `JWT_EXPIRES_IN`, `EXPIRY_ALERT_DEFAULT_DAYS`, `NOTIFICATION_POLL_INTERVAL_MS`, `NOTIFICATION_WITHIN_DAYS`, `RATE_LIMIT_WINDOW_MS`/`RATE_LIMIT_MAX`/`AUTH_RATE_LIMIT_MAX`/`RECIPE_RATE_LIMIT_MAX`, `BODY_LIMIT`, `CORS_ORIGIN`, `TRUST_PROXY`. Keep `.env.example` and the README/`docs/dev/developer-guide.md` env-var tables in sync when adding new ones — they've drifted out of sync before.
- `CORS_ORIGIN` defaults to `*` (dev convenience) with a startup warning outside `test` env; set an explicit comma-separated allow-list in shared/production environments.
- `TRUST_PROXY` defaults to `false`; set it (e.g. to `1`) when deployed behind a reverse proxy/load balancer, otherwise `express-rate-limit` will key on the proxy's IP instead of the real client IP.

## Architecture (Hexagonal / Ports & Adapters)
- `src/core/domain` and `src/core/ports` must stay free of infrastructure imports (no express, better-sqlite3, bcrypt, jsonwebtoken, pino, fetch, etc.) — they only reference port interfaces and Zod schemas.
- `src/application/*.service.ts` implement inbound port interfaces and depend only on outbound port interfaces (constructor-injected), never on concrete adapters.
- `src/adapters/inbound/http` — Express controllers/router/middleware (auth, rate-limit, request-logger), plus the OpenAPI registry (`openapi/`); `src/adapters/outbound/persistence` — SQLite + in-memory repositories (food items, users, health-check) and the migration system (`persistence/migrations/`); `src/adapters/outbound/recipe-provider` — Spoonacular adapter; `src/adapters/outbound/notification` — console notification adapter.
- All wiring (constructing adapters, injecting into services, injecting into controllers, starting the `NotificationPoller`, registering shutdown handlers) happens only in `src/index.ts`. When adding a new use case, add ports first, then application service, then adapter(s), then wire in `index.ts`.
- `InMemoryFoodItemRepository`/`InMemoryUserRepository` (`src/adapters/outbound/persistence/*.in-memory.repository.ts`) are used both as the `DB_PATH=:memory:` fallback in `src/index.ts` and as the backing repositories for HTTP integration tests. SQLite persistence has its own dedicated test suites (`*.sqlite.repository.test.ts`) exercising real on-disk databases, including legacy-schema migration scenarios.
- HTTP integration tests exist under `src/adapters/inbound/http/__tests__` using `supertest` against the real app built via `createApp` (see `test-app.ts` helper, which also wires `AuthService`/`AuthController` and exposes a `registerTestUser()` helper for getting an authenticated bearer token), wired to the in-memory repositories and real application services — no mocking at the HTTP layer except for the `RecipeProviderPort` (Spoonacular), which is faked since it's an external HTTP dependency.
- **Auth**: JWT bearer tokens (`AuthService` in `src/application/auth.service.ts`, `bcrypt` + `jsonwebtoken`). All `/api/v1/food-items`, `/alerts`, `/recipes`, `/shopping-summary` routes require `Authorization: Bearer <token>` (enforced by `src/adapters/inbound/http/middleware/auth.middleware.ts`); `/api/v1/auth/register`, `/api/v1/auth/login`, `/health`, `/health/ready`, and `/api/docs*` are public. Every `FoodItem` is scoped to a `userId`; every repository method takes `userId` and filters by it.
- **DB migrations**: `src/adapters/outbound/persistence/migrations/` contains a hand-rolled numbered-migration runner (`migration-runner.ts`) tracking applied migrations in a `schema_migrations` table. Both `SqliteFoodItemRepository` and `SqliteUserRepository` run the full migration list (`migrations/index.ts`) at construction. Each migration's `up()` must be idempotent-safe (`CREATE TABLE/INDEX IF NOT EXISTS`, checked `ALTER TABLE ADD COLUMN`) so it's always safe to run against a database that already has that change applied. The whole pending-migrations pass runs inside a single `db.transaction(...).exclusive()` call — this is load-bearing for correctness, not just style: it prevents a real, previously-reproduced race condition where concurrent connections to the same file could both apply (and crash on) the same migration. When adding a new migration, add a new numbered file, keep its `up()` idempotent, and add it to `allMigrations` in `migrations/index.ts` — never edit or renumber an existing migration once it may have shipped.
- **Logging**: structured logging via `pino` (`src/logger.ts`), level controlled by `LOG_LEVEL`, forced `silent` under `NODE_ENV=test`. Use `logger` (not `console.*`) in `application/`, `adapters/`, and `index.ts`; `core/domain`/`core/ports` must not import it. The one intentional exception is `SPOONACULAR_API_KEY`'s startup warning in `config.ts`, which uses `console.warn` to avoid a circular import (`logger.ts` imports `config.ts`). Never log raw caught error objects in `error-handler.ts` — body-parser attaches the raw unparsed request body (which may contain plaintext passwords) to `SyntaxError.body`; only log a safe subset (`name`/`message`/`stack`).
- **Hardening**: `helmet` (security headers), `cors` (allow-listed origins via `CORS_ORIGIN`), `express-rate-limit` (general limiter on all `/api/v1` + `/api/docs*` routes, stricter limiters on `/auth/register`, `/auth/login`, `/recipes/suggestions`), and a request body size limit (`BODY_LIMIT`) are all applied in `app.ts`/`router.ts`. Rate limiting is skipped by default under `NODE_ENV=test` (mirroring the logging-suppression pattern) so HTTP integration tests aren't affected; see `middleware/rate-limit.middleware.ts`'s `forceEnable` escape hatch for testing real 429 behaviour.
- **Graceful shutdown**: `src/index.ts` captures the `http.Server` from `app.listen(...)` and on `SIGTERM`/`SIGINT` drains in-flight HTTP requests (`server.close()`) *before* closing the SQLite connections, with a re-entrancy guard (duplicate signals are ignored) and a 10s force-exit backstop. When adding a new closeable resource (a new DB connection, a new poller, etc.), wire its shutdown into this same sequence in `index.ts` — don't rely on process-exit cleanup.
- **Containerisation**: `Dockerfile` (multi-stage, `node:24-slim`, runs as a non-root `app` user, no compiler toolchain in the final image) + `docker-compose.yml` (bind-mounts `./data`, healthchecks `GET /health`). See README's "Running with Docker" section.

## Module system
- Project uses native ESM (`"type": "module"`, `moduleResolution: NodeNext`). Relative imports within `src/` must use explicit `.js` extensions (e.g. `import { config } from './config.js'`) even though the source files are `.ts`.

## Node version
- Use Node 24 LTS per `.nvmrc` (`nvm use`).
